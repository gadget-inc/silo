Silo is built on top of SlateDB, which is a low-level key value store. Silo implements and maintain higher-level data-structurs within this KV store.

## Entities

### Job

One unit of work that should be attempted until completion or retries exhausted. Moves through states of `Scheduled`, `Waiting`, `Running`, `Succeeded`, `Retrying`, `Failed`, or `Cancelled`.

### Attempt

One attempt to run a unit of work. Moves through states of `Running`, `Succeeded`, `Failed`, or `Cancelled`.

### Task

One item that we need to dequeue and run. Usually, its a task for a worker to run an attempt, but there are other task types that represent internal operations that should happen after a point in time in the future. Most tasks need to be processed by the external worker that is polling Silo for what to do next, but some tasks are handled purely internally.

### Task lease

One task that has been leased by a worker. Upon leasing, a task is moved from the task queue into the task leases. A worker must complete the task or heartbeat for it before the lease expired, or else the system will assume the worker has crashed.

## Tenancy

All of Silo is built to house job data for multiple tenants, if necessary. All data for a single tenant lives in the same SlateDB database which ensures fast transactions for every hot-path operation. An individual tenant's data _can't_ be split across shards.

## Key/value layout

Silo uses the [storekey](https://crates.io/crates/storekey) crate for binary key encoding. This provides lexicographically-sortable binary keys that maintain correct ordering when compared as byte strings. Each key type has a unique single-byte prefix to ensure namespace isolation.

### Key types and their prefixes

| Prefix | Name | Description |
|--------|------|-------------|
| 0x01 | Job info | Stores job payloads: `(tenant, job_id)` |
| 0x02 | Job status | Stores job status: `(tenant, job_id)` |
| 0x03 | Status/time index | Secondary index for jobs by status, newest-first: `(tenant, status, inverted_timestamp, job_id)` |
| 0x04 | Metadata index | Secondary index for jobs by metadata key/value: `(tenant, key, value, job_id)`. The value holds the job's `enqueue_time_ms` as eight big-endian bytes (empty on an entry written before the listing index reached version 3), so a metadata-filtered listing of ids and enqueue times is served from the index alone. The entry carries the job record's row TTL and is deleted with the job. |
| 0x05 | Task | Work items in task order: `(task_group, start_time_ms, priority, job_id, attempt)` |
| 0x06 | Lease | Leased tasks: `(task_id)` |
| 0x07 | Attempt | Attempt records: `(tenant, job_id, attempt_number)` |
| 0x08 | Concurrency request | Jobs waiting for concurrency slots: `(tenant, queue, order, priority, request_id)`. `order` is a `u64` holding the start time in its low 56 bits and, for a priority-ordered row, the priority in its top byte (zero for a start-time-ordered row) |
| 0x09 | Concurrency holder | Tasks holding concurrency slots: `(tenant, queue, task_id)` |
| 0x0A | Job cancelled | Cancellation flags: `(tenant, job_id)` |
| 0x0B | Floating limit | Dynamic concurrency limit state: `(tenant, queue_key)` |
| 0x0C | Refresh task | Pending floating limit refreshes, one per queue per task group: `(task_group, tenant, queue_key)` |
| 0x0D | Enqueue-time index | Secondary index for a tenant's jobs newest-first: `(tenant, inverted_enqueue_time_ms, job_id)` |
| 0x0E | Status-segmented enqueue-time index | Secondary index for a tenant's jobs by status segment and priority, newest-first within each: `(tenant, segment, priority, inverted_enqueue_time_ms, job_id)`. The segment is one of `ScheduledFirst`, `ScheduledRetry`, `Running`, `Succeeded`, `Failed`, `Cancelled`; the value holds the next-attempt start time for the two Scheduled segments and is empty otherwise. A job has exactly one entry, moved on every status transition and deleted with the job; it carries the job record's row TTL. |
| 0xF0-0xFF | System | Internal counters, cleanup state, and metadata. Includes per-shard total/completed job counters (`0xF0`, `0xF1`), cleanup progress (`0xF2`-`0xF6`), per-queue concurrency requester counters (`0xF7`, recounted from the live request rows on every periodic counter reconcile pass), per-tenant status counters (`0xF8`) maintained via merge operator on every status transition, and the listing-index backfill's progress checkpoint and completion marker (`0xFB`, `0xFC`). The marker's value is the listing-index version the sweep completed: an empty value reads as version 1 (enqueue-time index built), version 2 means the status-segmented index is built too, and version 3 means every metadata index entry carries its job's enqueue time as well. The checkpoint records the version and pass it belongs to, and a checkpoint for another version is discarded. The query engine serves a listing from an index only when the marker is at or above that index's version. |

## Clustering approach

Silo works by separating the compute and storage tiers. Compute is provided by stateless or semi-stateless cloud compute, and storage is provided by cloud object storage. Compute can be deployed, rescheduled, or scaled at will. Data durability comes from object storage, not from the compute nodes themselves.

Within a cluster, all data is sharded. At any one time, each shard is opened and exclusively read or written to by a single compute node. The number of shards can grow over time by splitting shards. These shard leases are **permanent** -- they aren't locks with liveness checking. Instead, they persist through node crashes to prevent WAL data loss when using the split WAL mode. See [Permanent shard leases](#permanent-shard-leases) below for details.

### Shard splitting

When a shard becomes overloaded, it can be split into two child shards to distribute the load. Splits divide the tenant ID keyspace at a chosen split point:

- **Left child**: owns tenant IDs `[parent_start, split_point)`
- **Right child**: owns tenant IDs `[split_point, parent_end)`

The split point is always a tenant ID boundary, ensuring that all data for any individual tenant remains together in a single shard. This preserves tenant atomicity—Silo's concurrency queues and transactions operate within a single shard, so a tenant's data can never be divided.

The split operation proceeds through several phases:

1. **SplitRequested** — The split is initiated on the node owning the shard.
2. **SplitPausing** — Traffic to the parent shard is paused (clients receive retryable errors).
3. **SplitCloning** — The underlying SlateDB database is cloned for both child shards, then the shard map is atomically updated to replace the parent with the two children. The shard map update is the **commit point**.
4. **SplitComplete** — Children are active and ready to serve traffic. The split record is cleaned up.

After a split completes, each child shard contains cloned data from the parent. A background cleanup process then removes any data that falls outside each child's new range (defunct keys), followed by a compaction to reclaim storage.

For crash recovery, the shard map is the source of truth. If a crash occurs before the shard map update (commit point), the split is abandoned and the parent remains intact. Any orphaned clone databases are left behind but don't affect correctness—they're just wasted storage that can be garbage collected later. If a crash occurs after the shard map update, the split is committed and children exist in the shard map.

The clustering approach is modelled after something similar to Google Cloud Bigtable, where individual compute node members all hold leases over some subset of the overall shards. Unlike Bigtable, there's no central coordiantor managing which bits are assigned to which nodes. Instead, we just manage an internal hash ring that assigns the entire shard space to all the nodes, shifting around as few shards as possible when cluster membership changes.

### Shard coordination plan

Goals:

- Elastic compute membership with fast join/leave
- Shards are the atomic unit of load; clients specify a shard on each request
- Minimal downtime on ownership changes and no split-brain
- etcd is used only for control plane (membership, locks, handover), never per-request on the data plane

Key ideas:

- **Membership (ephemeral)**: Each node registers under `coord/members/<node_id>` with a membership lease (TTL, e.g. 10s). Value includes `{ addr, started_at, node_id, capabilities }`.
- **Ring computation**: All nodes watch `coord/members/` and deterministically build a consistent hash ring (e.g. Ketama with N virtual nodes per member).
- **Ownership**: The active owner of shard `<S>` is the node that holds the etcd key `coord/shards/<S>/owner`. Value: `{ owner_id, owner_addr, acquired_at }`. Unlike membership, shard ownership keys are **not** tied to any TTL-based lease -- they persist until explicitly released (graceful shutdown) or force-released (operator action).
- **Data plane independence**: Nodes serve a shard only if they currently hold its `owner` key and are active members. Requests never consult etcd; they rely on local in-memory ownership state maintained via watches/keepalives.

Node lifecycle:

1. **Join**

   - Create a membership lease (TTL ~10s, keepalive ~2s).
   - Put `coord/members/<node_id>` with the membership lease.
   - Scan for any shard leases already held by this node from a previous run (reclaim existing leases for WAL recovery).
   - Build ring from current `coord/members/*` and compute desired shard set.
   - Reconcile: for each desired shard, try to acquire `coord/shards/<S>/owner` via a put-if-absent transaction. Only start serving a shard after this key has been written.
   - Start watches on `coord/members/*` and `coord/shards/<S>/owner` for shards you own or are next-in-line for.

2. **Steady state**

   - Maintain keepalives for the membership lease. If keepalives fail (channel closes or prolonged error), immediately pause serving all owned shards to avoid split-brain.
   - On membership change event, recompute ring and run reconciliation: acquire new shards, release shards no longer owned.

3. **Graceful leave**

- Delete `coord/members/<node_id>` (using the membership lease), triggering ring recompute so contenders begin acquisition retries.
- Quiesce briefly per shard (1–2s) to drain in-flight work.
- Explicitly release each `coord/shards/*/owner` key for this node (delete-if-owner); new owners acquire on their next retry.

### Safe ring changes

On ring change, we must carefully change ownership of shards with minimal downtime. To do this, we ensure that the new owners start trying to acquire the shard lock before the old owners release it.

The flow:

1. A node either adds or removes its membership details under `coord/members/<node_id>`
2. All nodes discover this membership change, and update their in-memory hash rings, which shifts which shards they are responsible for.
3. New shard owners immediately start trying to acquire the lease for the shards they want to own. Each runs a jittered loop: try `Put` of `coord/shards/<S>/owner` using "create only if not exists" semantics (i.e., CAS on missing key). If exists, backoff and retry; never overwrite.
4. Old shard owners wait a little bit, ensuring that the new shard owners discover the change and begin their retry loops in advance.
5. Old shard owners start relinquishing their shard locks (explicit delete-if-owner), and stop serving requests for those shards when that's happened.

Crash case: the previous owner's shard lease persists (see [Permanent shard leases](#permanent-shard-leases)). An operator must force-release the lease via `siloctl shard force-release` before another node can acquire it.

### Correctness and split-brain avoidance

Only the node holding `coord/shards/<S>/owner` **and** with active membership may serve `<S>`. All others must return NOT_OWNER immediately. Nodes must pause serving a shard if their membership keepalive fails, even if they still hold the shard lease, because another node might need to take over.

Failure modes:

- **Crash**: shard leases persist (permanent). The crashed node retains its shard leases, preventing another node from accidentally opening the shard and losing WAL data. When the node restarts with the same `node_id`, it reclaims its leases and recovers the WAL. If the node is permanently lost, an operator must force-release the shard leases via `siloctl shard force-release`.
- **Network partition**: owner loses membership keepalive; it must cease serving. Unlike a crash, the shard lease is still held, so no other node can acquire it until it's released or force-released.
- **Simultaneous join**: consistent hashing minimizes movement; CAS on `owner` guarantees single winner.

### Permanent shard leases

Shard leases are **permanent** -- they are not tied to any TTL-based lease and survive node crashes. This is critical for preventing WAL data loss when using a local filesystem for the write-ahead log.

**Why permanent leases?** When a node writes to a shard, data first goes to the local WAL before being flushed to object storage. If a node crashes before the WAL is flushed, that data only exists on the crashed node's local disk. If another node were to immediately acquire the shard (as would happen with TTL-based ephemeral leases), it would open the shard from object storage and miss the unflushed WAL data, causing data loss.

With permanent leases:

1. **Node crashes** -- the shard lease persists, blocking other nodes from acquiring the shard.
2. **Node restarts** -- if the node restarts with the same `node_id` (e.g., a Kubernetes StatefulSet pod), it finds its existing shard leases, reclaims them, opens the shard databases, and recovers the WAL data from local disk. No data is lost.
3. **Node permanently lost** -- if a node will never come back, an operator uses `siloctl shard force-release <shard-id>` to release the lease. The operator accepts that any unflushed WAL data on that node is lost. Another node then acquires the shard and starts serving it from the last state in object storage.

**Configuration for permanent leases**: For permanent leases to work correctly across restarts, the `node_id` must be stable. In Kubernetes, set `node_id = "${POD_NAME}"` so that a restarted StatefulSet pod re-acquires its own leases. If `node_id` is not configured, a random UUID is generated on each startup, meaning a restarted node won't reclaim its previous leases.

**When local WAL is not used**: If the WAL is stored in object storage (same backend as the main data), permanent leases still apply but are less critical -- there's no local data to lose on crash. An operator could force-release shards from a crashed node without risking data loss in this configuration.

### Request handling and redirection

On each RPC, the server checks a local map of owned shards. If not the owner, return NOT_OWNER with an optional hint `{ owner_id, owner_addr }` read from the cached `owner` value. Clients retry a few times and may redirect using the hint. Servers never query the coordinator on the request path.

## Task broker

Each task group on a shard has a broker: an in-memory buffer of ready tasks that dequeues claim from, filled by a background scan of the task group's key range (prefix `0x05`). Task keys sort by start time, so the buffer and the claims from it are in start time order.

### Scan floor

SlateDB keeps a tombstone for every deleted row until a compaction removes it, and a range scan steps over each one. A task group that has dequeued many tasks has that many tombstones at the head of its range. So a scan does not start at the head: it starts at the broker's **scan floor**, the start time below which every task row has already been dealt with (buffered, claimed and in flight, suppressed by an ack tombstone, or deleted as belonging to another shard). A scan that reads to the end of the range, or to the first future-dated row, moves the floor to the current time. A scan that stops early, at its batch limit or because the buffer is full, moves the floor only to the last row it read, so a task group with more ready rows than the buffer holds has a floor that lags behind the rows not yet buffered.

Every path that writes a task row tells the broker the row's key, once before the write is issued and again when it is durable. What the broker does with it depends on the row's age:

- A row whose start time is within `broker_keyed_read_min_lag_ms` (default 1000) of the current time lowers the floor to that start time, and the next range scan reads it. One short range scan serves a burst of recent writes more cheaply than a point read per row.
- An older row leaves the floor where it is, and the broker holds its key. Before a scan reads its range it **reads by key** each held key that sorts below its floor, running the row through the same checks a scanned row gets. A held key at or above the floor is left to the range.

The second case exists because some rows are old when they are written. A job granted a concurrency slot after waiting keeps its original start time in its task key, so that it is claimed ahead of newer jobs instead of going to the back of the buffer. Lowering the floor to such a row would make the next scan step over every row and tombstone written since the job was enqueued, once per grant, for as long as the queue is draining its backlog. A point read costs the same whatever the row's age.

Only keys below the floor are read by key because of claim order. A row below the floor is older than every row the range has left to read, so buffering it first keeps tasks in start time order. A row above a lagging floor is not: reading it by key would buffer it ahead of older rows the range has not reached. The range reads it when it gets there.

The row's age decides, not its distance from the floor, so an old row never holds the floor back: not while the floor is at the current time, not while the floor is itself old, and not while a scan of the whole range is running and there is no floor to compare with.

A held key leaves the broker in one of two ways. One below the floor is settled by its point read. One at or above the floor is dropped when a scan that began after it was noted ends: the row was in that scan's view, so the scan either dealt with it or stopped short of it, and the floor a scan leaves is never above a row it could see and did not deal with. A key noted while a scan runs may describe a row the scan's view does not include, so it is kept for the next scan, which reads it by key if the floor has moved past it and drops it otherwise.

The broker holds at most `broker_keyed_read_max_keys` keys (default 8192, the size of the buffer). With that many held, a further old row lowers the floor instead, so a row that does not fit is still found, by a range scan that costs more.

A point read can race the write it is reading for, so the broker settles each read against the key's state from before the read was issued. A key noted again while its read was in flight (its write reported durable, or its row released from an abandoned dequeue) is kept for the next scan whatever the read returned. A read that finds no row drops the key only if the write was already durable when the read was issued, which means the row has since been dequeued, cancelled or rewritten. A key whose write is not yet durable is read once, so a row visible before its write is durable is buffered early, and then left until the write is reported.

### Full rescan

Once every `broker_full_rescan_interval_ms` (default 60000) a scan ignores the floor and reads the whole range. It finds any row a writer did not report. Every held key is in its range, so it drops each one noted before it began, which is how a key whose write never happened leaves the broker.

A full rescan steps over every tombstone in the range, so its cost follows their number. Two other scans share that cost: a new broker's first scan, which has no floor yet, and the scan after an old row lowers the floor because no more keys could be held, which reads from that row's start time.

## Concurrency Queues

Concurrency queues limit how many jobs with the same queue key can run simultaneously. They work like a ticket system: a job must hold a ticket for a queue before it can proceed to execution, and each queue has a limited number of tickets available.

### Requesters and holders

The two key concepts are **requesters** and **holders**:

- A **holder** is a task that has been granted a ticket and is occupying one of the queue's concurrency slots. It's either currently running on a worker, sitting in the task queue waiting to be picked up, or in the process of being leased. Holders are stored durably in SlateDB (prefix `0x09`) and also tracked in an in-memory set for fast capacity checks.

- A **requester** is a job that wants a ticket but the queue is full. Requesters are stored durably in SlateDB (prefix `0x08`), ordered so the most eligible job is first in the scan. With `concurrency_request_priority_order` on, a requester is written priority-ordered and sorts by `(priority, start_time, request_id)`; with it off (the default) it is written start-time-ordered and sorts by `(start_time, priority, request_id)`. Both kinds can sit in one queue: the top byte of a key's ordering field is its band, the priority for a priority-ordered requester and 0 for a start-time-ordered one, and a queue sorts by band, then start time. Start-time-ordered requesters are therefore served ahead of priority-ordered ones of priority 1 and up. Priority order has no aging: a requester waits for as long as higher-priority requesters keep arriving. Requesters don't have a corresponding task in the task queue — they're parked, waiting for a holder to finish and free up a slot.

When a holder finishes (or is cancelled), the system promotes the next eligible requester into a holder — this is the core "release and grant next" operation.

Each holder record stores the time it was granted plus the owning `job_id` and total `attempt_number`, so the `queues` SQL table can show which job holds a slot. A record that carries no owner decodes with those fields absent and is treated as owner-unknown.

### Grant scanner

Promotion is done by the grant scanner, a per-shard task that is woken for a `(tenant, queue)` whenever a holder is released, a floating limit is raised, or the periodic reconcile sweep finds a requester counter above zero. An invocation reads the queue's requester records in key order (band, then start time), starting at the queue's request floor (see [Request floor](#request-floor)): first the records noted below the floor, one point read each, then a range scan that is a snapshot of the queue taken when it opens, after the invocation began. It skips from the first record that starts in the future to the next band, then validates each candidate against a fresh read of its job's status row: only a `Scheduled` job on the request's attempt number is granted, and a request whose job is missing, terminal, or on another attempt is stale. The scanner re-reads a stale request's row before acting on it. A row still present is deleted and the queue's requester counter decremented for it. A row that is gone is left alone: the cancel or reimport that made the request stale deleted the row and decremented the counter in the same commit as its status change, so a second decrement would leave the counter below the number of live requests. Each such skip is counted in `silo_concurrency_grant_vanished_requests_total{shard}`.

An invocation grants at most the number of slots it was woken for and walks a bounded number of requester records, so it can end while the queue still has free slots and waiters: a release wakes the scanner for one grant however many slots are free, and a raised floating limit can free more slots than one walk reaches. When an invocation granted or deleted at least one record and stopped before the end of the queue's ready records with capacity still free, the scanner queues a follow-up invocation for the queue, counted in `silo_concurrency_grant_unfilled_capacity_passes_total{shard}`. Follow-ups are served behind release-driven wake-ups, a bounded number of queues per scanner iteration (`grant_scanner_cold_batch_size`), and each one asks for `grant_scanner_commit_chunk_size` grants, so a queue working through a large backlog fills one commit chunk per iteration until it is full or has no eligible waiter left, while other queues' releases are served in every iteration. An invocation that changes nothing queues no follow-up; such a queue is picked up again by the periodic reconcile sweep.

A status row written at or after the invocation began cannot vouch for a request read from the snapshot. The job may have been cancelled, deleted and enqueued again under the same id, or reimported, and the path that replaced it deleted the request row and decremented the requester counter already; granting the snapshot's copy would hand the replacement job a slot its own chain knows nothing about and decrement the counter a second time. So before reserving a slot for a candidate whose status changed at or after the invocation's start time, the scanner re-reads the candidate's request row, and skips the candidate without a grant, a holder, a delete, or a counter change when the row is gone. Each skip is counted in `silo_concurrency_grant_vanished_requests_total{shard}`. A candidate whose status predates the invocation is granted without the extra read.

A cancel or a reimport can also arrive while a pass is under way, after the pass has read a job's status and before it commits that job's grant. Each queue has an in-memory request-row lock for this. A scanner pass holds the queue's lock exclusively from its status reads to its last commit. Cancel and reimport hold it shared, for every concurrency queue in the job's limits, from before they look up the job's request rows until their transaction commits; shared holders do not block one another. So a cancel either commits before the pass reads the job's status, and the pass treats the request as stale, or it waits for the pass. In the second case the pass grants the request and the cancel finds no request row to delete. Its serializable commit then conflicts with the task row or status the pass wrote, so it retries, finds the granted task, and deletes it together with its holders. A cancel of a job waiting on a queue can therefore wait for one scanner pass over that queue.

### Request floor

Granting or cancelling a request deletes its record, and SlateDB keeps each delete as a tombstone until a full compaction. A scan that opens at the start of a queue's requester records steps over every tombstone ahead of the first live record, so its cost grows with the grants made since the last compaction. Each shard therefore keeps in memory, per queue, a **request floor**: a key below which every requester record is dead, apart from records whose keys the floor has **noted**. A scanner invocation point-reads the noted keys below the floor in key order, then opens its range scan at the floor. `silo_concurrency_request_floor_lag_ms{shard}` records how far in the past each invocation's floor lies.

An invocation moves the floor when it ends, over what it proved dead: records its scan returned whose delete it then committed (a grant or a stale request), or which it read back as already gone. The floor stops at the first record the scan returned and the invocation left in place, whatever the reason: the queue ran out of capacity, the requested count was reached, the record's next limit is saturated, a read failed, or the record starts in the future. A record a pass leaves is therefore the first thing the next pass scans.

An invocation whose scan opened at the start of the queue's records and ran to their end, with every record it returned dead, proved the whole queue dead, and any key is then a sound floor. A rebuilding pass (below) that ends this way puts back the floor it dropped, so a queue that has drained keeps its floor while invocations keep finding it empty. An invocation that began with no floor and read no record sets a **whole-queue floor**: the last band at the time the invocation began, above every record with an earlier start time. Under a whole-queue floor a write counts as close by its start time whatever its band, so the first record that arrives with a current start time lowers the floor to its key and later passes scan from there, while a record that arrives with an old start time is noted and read by key.

The gaps between the keys a scan returned held no record at the scan's snapshot, and a record can be written into one afterwards. So every writer of a requester record tells the floor twice. Before its batch commits it notes the record's key, and once the commit has succeeded it confirms the write. A key stays noted until a pass that began after the confirmation has dealt with the record, because an earlier pass's snapshot may not show it and that pass may move the floor past it. A noted key below the floor is read by key on every pass until its record is granted or deleted. A read that finds no record retires the key when the write was confirmed before the pass began, since the record has been deleted, and keeps it otherwise. A writer whose batch fails, is retried under a new key, or whose future is dropped never confirms; its key is kept for 10 seconds, the time allowed for SlateDB to apply a batch whose submitting future was cancelled, and then retired on a read that finds no record. Reads by key are counted in `silo_concurrency_request_noted_reads_total{shard, outcome}` and unconfirmed writes in `silo_concurrency_request_writes_abandoned_total{shard}`.

A record can be written far below the floor. A job that wins a slot on one limit and then waits on the next is keyed with its original start time, so when queues with backlogs of different ages feed one queue, records reach that queue hours below its floor; and a higher-priority arrival lands in a band below the one being drained. Such a write leaves the floor where it is and the record is served by its point read. A write that lands in the floor's band, at most `grant_scanner_request_floor_min_lag_ms` (default 1000) of start time below the floor, lowers the floor to its key instead, since a scan from there steps over little. Set to `72057594037927936` (2^56) or above, the setting lowers the floor for every write below it and no record is read by key. A queue keeps at most `grant_scanner_request_noted_max_keys` (default 4096) keys noted below its floor; a write past that lowers the floor to its key and is counted in `silo_concurrency_request_noted_overflows_total{shard}`.

The floor is rebuilt on a timer. Once a queue's floor has been in use for `grant_scanner_request_floor_rebuild_interval_ms` (default 60000), the next invocation drops it and reads from the start of the queue's records, so a record that reached the queue without telling the floor waits at most one interval. The rebuilding pass is also the only one that finds a record whose write committed more than 10 seconds after its writer stopped waiting for it, so an interval too long to elapse leaves such a record unread. The rebuilding pass counts each record it finds below the dropped floor with no note in `silo_concurrency_request_floor_rebuild_rows_total{shard}`, which should stay at zero. Floors are not persisted, and the periodic reconcile sweep drops the state of a queue that has no invocation in flight, no unsettled write and a floor past its rebuild interval. A queue with no floor is read from the start by its next invocation, which sets one. With `grant_scanner_request_floor = false` no floor is kept and every invocation reads from the start of the queue's records.

Three shapes get nothing from the floor. A record left at the front of a queue while records behind it are granted, such as a front deferred by a saturated next limit or a future-dated record at the head of a band, holds the floor in front of it, and each pass steps over the tombstones behind it. A whole-queue floor lowered to a record in a band above one that was drained leaves the drained band's tombstones in front of each pass until a record at or past them is read. And each rebuild, and the first invocation of a queue with no floor, walks the queue's whole range once.

The look at a queue's head waiter that picks the task group of a scanner-originated floating refresh reads the same way, noted keys and then a scan from the floor, and moves nothing.

### Orphan holder sweep

A holder can outlive its task: if the expired lease reaper reaps its lease and nothing ever reports an outcome for the task, the holder row stays behind and occupies a slot forever. On the periodic concurrency-reconcile tick, each shard walks its durable holder rows in bounded slices (`orphan_holder_sweep_slice` rows per tick, resuming from a cursor) and classifies every holder older than `orphan_holder_grace_ms` using point reads only:

- An unexpired lease for the holder's task means the holder is **live**. An expired lease row still awaiting the reaper does not count.
- When the record names an owner, a missing job status row, a terminal status (`Succeeded`, `Failed`, `Cancelled`), a `Running` job with no lease for this task, or a `Scheduled` job on a different attempt all mean the holder is an **orphan**.
- A `Scheduled` job on the holder's own attempt (a chain parked between limits, or a task still waiting in the task queue) and an owner-unknown record, which has nothing to check, are both **live** until they pass `orphan_holder_stale_ms`, after which a lease-less holder is an orphan regardless of owner.

A holder is purged only after two consecutive full passes classify it as an orphan, so a snapshot racing an in-flight grant or lease write never releases a live slot. Purging deletes the durable row, releases the in-memory reservation, and wakes the grant scanner for the queue so a waiting requester can be admitted. Every purge is logged at `warn` with the tenant, queue, task id, owner, and reason, and counted in `silo_concurrency_orphan_holders_purged_total{shard, reason}`.

The stale rule trades safety for recovery: a chain parked between limits or a task waiting in the task queue for longer than the threshold can lose its holder, and the queue then over-admits by one slot. That is the same tradeoff the web UI's Drop holders action makes for a whole tenant, applied here to one holder at a time. The `Running`-without-lease rule can likewise purge the holder of a worker whose lease lapsed before the reaper ran; the reaper is about to fail that attempt anyway. The sweep never touches leases, tasks, requests, or job status.

### Console actions

The tenant page of the web UI offers two operator actions on a tenant's concurrency state, each an RPC routed to the tenant's owning shard. **Drop holders** deletes every concurrency holder row for the tenant and releases the in-memory reservations, so a tenant wedged by leaked holders can be granted slots again; in-flight attempts keep running and may briefly double-run. **Recount requesters** recounts every per-queue requester counter for the tenant from the queue's live request rows and merges the difference, the same correction the periodic counter reconcile pass applies to every queue on the shard, so an operator can repair a known-bad tenant without waiting for the next pass. It is safe on a live tenant: the count and the counter are read at one snapshot, and concurrent enqueues, grants and cancels only add their own deltas on top. Both report what they changed.

### Why in-memory counts?

Checking concurrency capacity requires knowing how many holders exist for a queue. Scanning the durable holder keys in SlateDB on every enqueue or grant would be too slow, so we maintain an in-memory `HashMap<queue, HashSet<task_id>>` of current holders (`ConcurrencyCounts` in `src/concurrency.rs`). This makes capacity checks a fast set-size lookup.

The in-memory counts are **lazily hydrated**: the first time a queue is accessed, we scan its durable holder keys to populate the set. After that, the in-memory state is kept in sync by updating it on every grant and release. The hydration scan filters by shard range to avoid double-counting holders that were cloned during a shard split.

The tricky part is keeping in-memory counts consistent with durable state. We use an **optimistic reservation** strategy: in-memory counts are updated *before* the DB write, and if the write fails, the caller must invoke explicit rollback methods. This eliminates any TOCTOU window where two concurrent operations could both see available capacity and double-grant.

### Enqueue flow

When a job with concurrency limits is enqueued, limits are processed sequentially:

1. **Immediate grant**: Check the in-memory holder count against `max_concurrency`. If there's room and no job is waiting on the queue, atomically reserve a slot in memory, write a holder record to the batch, and advance to the next limit.

2. **Queued**: If the queue is full and the job is ready to run now, write a requester record to the batch. No task goes in the task queue — the job is parked until a slot opens. A job that finds room while the queue's requester counter is above zero is queued the same way, so the free slot goes to the grant scanner's pick and not to whichever job arrived last; the grant scanner is nudged for the queue once the requester record is durable. A due `RequestTicket` and a chain reaching its next queue follow the same rule. The counter is a durable read, so a requester still in an uncommitted batch is not seen. Slots in the live-headroom share (`grant_scanner_live_headroom_fraction`), which the scanner never fills, are still taken by arriving jobs directly.

3. **Future-scheduled**: If the queue is full and the job has a future start time, write a `RequestTicket` task to the task queue at that start time. When it fires, it re-attempts the grant.

4. **All limits passed**: Once every limit is satisfied, a `RunAttempt` task is written to the task queue. This task carries a `held_queues` list of all concurrency queues it holds tickets in, which is used to release them when the task completes.

### Multiple limits per job

Jobs can specify multiple limits (concurrency, floating concurrency, and rate limits) which are checked in order. `enqueue_limit_task_at_index` loops through them, accumulating granted queues as it goes:

- Each granted concurrency limit adds its queue to the `held_queues` list.
- If any limit blocks, the function returns early. The job resumes from that limit index when the blocking condition clears.
- Rate limits work differently — they create a `CheckRateLimit` task, and when that passes, the limit loop continues from where it left off with the accumulated `held_queues`.
- When all limits pass, the final `RunAttempt` task gets all the `held_queues`.

On retry, limit processing restarts from scratch — the job must re-acquire all concurrency tickets.

### Single live terminal row per attempt

A task key ends in a write-time `epoch_ms` that disambiguates a rewritten key from the broker's ack tombstone of its just-deleted predecessor; it is not part of task identity. The invariant that at most one terminal task row (`RunAttempt` or `CheckRateLimit`) is live per `(job_id, attempt)` is enforced by the duplicate-materialization guard at every chain re-entry point — the grant scanner's reserve loop, `handle_request_ticket`, and `handle_check_rate_limit`. Before continuing a chain, each consults `live_terminal_row_exists` (a durable prefix scan at the attempt's candidate start times) plus a per-batch seen-set for rows the current uncommitted batch already wrote, and drops any second grant source for the attempt (a duplicate request row, a replayed ticket, or a replayed rate-limit continuation) instead of materializing a coexisting row at a fresh epoch. Status-driven lookups (`find_task_by_identity` in cancel, expedite, reimport, and lease) rely on this when they act on the single row their prefix scan returns. The grant scanner reads its prefix scans a window of candidates at a time, concurrently; a window holds at most `grant_scanner_commit_chunk_size` candidates, no more than the queue has free slots, and no more than the invocation has grants left to make. `silo_concurrency_grant_duplicate_checks_total{shard}` counts those scans.

### Floating max concurrency limits

Silo supports concurrency queues who's max concurrency is adjusted continuously over time. This allows queues to be adjusted by operators, as well as by automated controllers trying to achieve some setpoint in some other system, like rate limit usage of a downstream API.

Floating max concurrency limits are specified by each job when the job is enqueued, which puts the job in that concurrency queue. The max concurrency for that queue is defaulted to an initial value, and then periodically refreshed. If too many jobs are currently running, no more will start until the queue is below its new max concurrency, and likewise if the queue now has more headroom, more jobs will start. The max concurrency value for the queue is refreshed by sending a special type of refresh task to any listening Silo worker, which can then run whatever fancy business logic necessary to compute a new value.

We're careful to only push refresh tasks for queues that are actively in use.

### Gubernator rate limiting

Incoming jobs may specify that they need to pass a Gubernator rate limit to proceed. For each attempt, Silo will make RPCs to Gubernator to check these rate limits before allowing the attempt to run. This is done by enqueuing and running a task that polls the rate limit in Gubernator. If the rate limit passes, we enqueue the actual task to run the attempt, and if it doesn't, we re-enqueue a task for the future to poll the rate limit again.

# Big decisions

## Do we group data by tenant or not?

Silo currently groups all the data for a given tenant into the same SlateDB instance. This has major performance benefits, as all transactions for the hot path can transact locally, in-memory, on the one compute node that has that tenant's shard open. This allows for much higher throughput and lower resource utilization than something that uses consensus or distributed transactions for every state change. When using a local WAL for maximum performance, permanent shard leases ensure the node retains shard ownership through crashes, allowing WAL recovery on restart without data loss.

There's a couple downsides to this:
 - there is a maximum scale any one tenant can reach. It is different for different workloads, but we've measured it to be about 4k jobs / second / shard.

The alternative would be to not group data by tenant, and instead spread every tenant's data out across a subset (or all) shards in the cluster. This would allow for much higher scale per individual tenant, as you could bring the full might of the cluster to bear on a single tenant's workload. We deemed the downsides of this approach too severe however: 
 - Silo's concurrency queue primitive offers global coordination, where jobs on different shards would need to collaborate to only let the max concurrency proceed at any one time. With cross-shard data storage, we'd need to build an expensive and complicated distributed transaction or inbox/outbox system for mutating data on different shards.
 - Introspection queries get more expensive, as now all of them need to do a scatter-gather to check all data on all shards in the system, rather than just routing directly to the shard storing data for a given tenant.

Temporal and Restate both take the more fundamentally scalable approach of not grouping data by tenant, but offer a higher cost per state change because of this.
